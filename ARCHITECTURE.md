# jade.tools

Локальный **мультитул** — набор небольших инструментов, который запускается на
вашем ПК и открывается в браузере. Один Flask-сервер, единый тёмный
(jade-зелёный) интерфейс на Lucide-иконках, общая инфраструктура задач/настроек.
Можно держать в системном трее и в автозапуске.

Все три инструмента работают не только с YouTube — под капотом везде `yt-dlp`,
а значит подойдёт ссылка с **любого сайта, который он поддерживает**
(TikTok, Instagram, Vimeo и многие другие; плейлисты целиком — только с
YouTube, см. «скачать» ниже).

> Архитектура сделана так, чтобы **легко добавлять новые тулзы**: цель проекта —
> постепенно превращать его в многофункциональный локальный комбайн.

## Что уже умеет

| Инструмент | Модуль | Что делает | URL |
|-----------|--------|------------|-----|
| **скачать** | `tools/youtube.py` | видео, звук и **плейлисты целиком** с YouTube (и др. сайтов) через yt-dlp: режимы видео+звук / только видео / только звук, выбор разрешения, формата контейнера (mp4/webm/mkv) и аудио (mp3/m4a/wav/opus); для плейлиста — выбор видео чекбоксами, доставка архивом (.zip) или потоково | `/youtube/` |
| **сжать** | `tools/compress.py` | уменьшает видео до заданного размера в МБ двухпроходным x264 (точное попадание в размер). Источник — файл с диска **или** ссылка (YouTube и другие сайты через yt-dlp). Можно понизить разрешение и битрейт звука | `/compress/` |
| **нарезать** | `tools/trim.py` | вырезает фрагмент из аудио **или** видео. Источник — файл или ссылка (YouTube и другие сайты через yt-dlp; ролик качается во временную папку в выбранном разрешении). Волна + видеоряд с зумом, выбор аудиодорожки (если их несколько), опциональное сжатие фрагмента, плеер | `/trim/` |
| **настройки** | `tools/settings.py` | общие настройки скачивания/путей/очистки для всех инструментов | `/settings/` |

Лендинг (`/`) показывает плитки `скачать`/`сжать`/`нарезать` (берутся из реестра
автоматически). «Настройки» — отдельный раздел, не плитка: иконка-шестерёнка
внизу левой панели навигации, под остальными пунктами, с разделителем.
Внизу главной страницы — строка версии (`#versionTag` в `index.html`,
прижата к низу окна и отцентрована по контентной области — без учёта
навигационного рейла: `left:var(--rail-w); right:0`).

## Архитектура

Ключевая идея — **реестр инструментов**. Сервер ничего не знает про конкретные
тулзы: он просто подбирает их из пакета `tools/`.

```
app.py                # Flask-сервер: лендинг + общие роуты задач (status/cancel/file)
core.py               # общая инфраструктура: задачи, настройки, cookies/Deno, кэш, уборщик
settings.json          # настройки приложения (создаётся сам, см. раздел «Настройки»)
tools/                # пакет инструментов
├── __init__.py       #   реестр: список ALL, функции blueprints() и tools()
├── youtube.py        #   инструмент «скачать»
├── compress.py       #   инструмент «сжать»
├── trim.py           #   инструмент «нарезать» (аудио и видео)
└── settings.py       #   страница настроек (НЕ в ALL — регистрируется отдельно в app.py)
templates/
├── _base.html        # общий каркас: стили (jade-тема), Lucide-иконки, сайдбар, навигация
├── index.html        # лендинг с плитками
├── youtube.html      # UI «скачать»
├── compress.html     # UI «сжать»
├── trim.html         # UI «нарезать»
└── settings.html     # UI страницы настроек
tray_app.py           # запуск сервера в фоне + иконка в системном трее (для .exe)
build.bat / jade.spec # сборка .exe через PyInstaller (onedir)
make_clean_zip.bat    # whitelist-экспорт проекта в .zip (для ревью кода / GitHub)
make_icon.py          # генерация logo.ico из logo.png
_internal/            # (только в собранном виде) ресурсы PyInstaller — не трогать
bin/                  # yt-dlp.exe/ffmpeg.exe/ffprobe.exe/deno.exe, плоско; создаётся сам
temp/                 # временные рабочие файлы задач; создаётся сам
cache/                # кэш скачанных роликов; создаётся сам
logs/                 # лог работы приложения (отдельно от temp/cache); создаётся сам
```

Все четыре папки (`bin/`, `temp/`, `cache/`, `logs/`) по умолчанию создаются
**рядом с exe** (портабельность — см. «Резолвинг зависимостей» ниже и раздел
«Пути» в настройках, где `temp`/`cache` можно переопределить).

### `core.py` — общая инфраструктура

То, что переиспользуют все инструменты:

- **Система задач `JOBS`** — словарь `job_id → job` под `JOBS_LOCK`. У задачи
  есть статус (`pending|fetching|ready|downloading|processing|done|error|canceled`),
  прогресс 0–100, скорость/ETA, текстовый этап (`stage`), путь к результату,
  ссылка на активный `subprocess` (для отмены). `new_job()`, `job_dir()`,
  `cleanup_old_jobs()` (хранит последние 20 завершённых), `cleanup_all_jobs()`
  (чистит всё при выходе).
- **Система настроек** — `DEFAULT_SETTINGS`, `load_settings()` /
  `save_settings(partial)` / `reset_settings()` / `get_settings()`, и
  `apply_settings()`, которая после каждого изменения пересобирает рабочие
  пути (`DOWNLOADS_DIR`, `CACHE_DIR` — резолвятся по режиму `temp_mode`/
  `cache_mode`, см. «Пути: три режима и фоллбэк»), источник cookies
  (`YT_COOKIES_BROWSER`/`YT_COOKIES_FILE`) и ограничение скорости (`_RATE_LIMIT`,
  переданное в `--limit-rate`; биты пересчитываются в байты). Хранится в
  `settings.json` рядом с приложением. Подробности значений — раздел «Настройки».
- **Кэш скачанных роликов** — `cache_get(key)` / `cache_put(key, path)`. Если
  тот же YouTube-ролик в той же спецификации (качество/формат/режим) уже
  качался, файл переиспользуется вместо повторного скачивания. Лежит в
  `CACHE_DIR/<sha1(key)>/`, кэш живёт `CACHE_TTL` (6 ч) с последнего
  обращения, и его не трогает обычный уборщик задач. Если папка кэша
  недоступна (`CACHE_AVAILABLE=False`) — обе функции no-op, кэш просто
  выключен, без попытки писать в недоступный путь.
- **Резолвинг внешних зависимостей** (`resolve_dependency()` /
  `refresh_dependencies()` / `dependency_status()` в `core.py`) — единый
  порядок поиска каждого бинарника (`yt-dlp`, `ffmpeg`, `ffprobe`, `deno`):
  `bin/` (рядом с exe, плоско) → системный `PATH` (`shutil.which`; для Deno —
  через `ensure_js_runtime_on_path()`) → «отсутствует» (без падения
  приложения). Результат — резолвнутые пути `YT_DLP_BIN`/`FFMPEG_BIN`/
  `FFPROBE_BIN`/`DENO_BIN`, которые подставляются во все subprocess-вызовы
  вместо голых строк `"yt-dlp"`/`"ffmpeg"`/`"ffprobe"`/`"deno"`. `ffmpeg` и
  `ffprobe` — два разных бинарника, резолвятся и проверяются независимо
  («ffmpeg есть, ffprobe нет» — зависимость неполная). `missing_dependencies(tool_id)`
  / `missing_dependencies_payload(tool_id)` проверяют набор, нужный конкретному
  инструменту (`TOOL_DEPENDENCIES`: «скачать» — все четыре, Deno заранее, в
  одном ряду с остальными, а не реактивно после ошибки JS-проверки; «сжать»/
  «нарезать» — только ffmpeg+ffprobe), и используются в API-роутах для
  понятной, структурированной (`{missing_deps, need_install}`) ошибки ДО
  начала операции — по ней фронт открывает окно установки (см. «Установка и
  обновление зависимостей» ниже).
- **Cookies + JS-рантайм для YouTube** — `cookies_args()` собирает
  `--cookies-from-browser` (режим «авто из браузера», не устаревает — куки
  читаются заново при каждом скачивании) либо `--cookies <file>` (свой
  экспортированный `.txt`, может устаревать со временем). `ensure_js_runtime_on_path()`
  при импорте подмешивает в `PATH` установленный через winget **Deno** — он
  нужен yt-dlp для решения JS-проверок YouTube (signature/n challenge); без
  него web-клиент отдаёт только превью-картинки. `ytdlp_cmd(..., cookies=…)`
  подмешивает cookies только по явному указанию вызывающего кода — сам он их
  не решает; `--remote-components ejs:github` (EJS solver) добавляется
  автоматически, но только для youtube.com/youtu.be — на прочих сайтах он не
  нужен.
- **Cookies «по мере необходимости», но не вслепую** — какая попытка идёт
  первой, зависит от настройки «автоматически брать cookies из браузера»
  (`_first_attempt_cookies()` в `core.py`): если включена (по умолчанию) —
  первая попытка сразу С cookies (YouTube их почти всегда требует, так что
  попытка без них заведомо в пустую); если выключена — первая попытка
  по-прежнему БЕЗ cookies, как раньше. В обоих случаях вторая попытка — в
  противоположную сторону: это не «на всякий случай», а осознанный fallback —
  без него ломается сценарий TikTok (стабильный HTTP 403 с устаревшими
  cookies из общего файла/браузера, но мгновенная отдача без них — см. ниже).
  Реализовано в `run_ytdlp_json_ex()`, `detect_playlist()` и
  `run_ytdlp_download()`; подробности — раздел «Cookies и доступ к YouTube».
- **Метаданные yt-dlp** — `run_ytdlp_json_ex(url)` (`--dump-single-json`,
  таймаут 120 с) для полных метаданных одного видео и `detect_playlist(url)`
  (`--flat-playlist --dump-single-json`, таймаут 90 с) — быстро отличает
  ссылку-плейлист от одиночного видео. Для плейлиста `--flat-playlist`
  действительно не вытягивает полные форматы каждого дочернего видео (ради
  чего он и используется — иначе упирались в 120-секундный таймаут), но для
  ссылки на **одиночное** видео флаг ни на что не влияет — yt-dlp всё равно
  извлекает данные целиком, включая `formats` (проверено эмпирически на
  YouTube и TikTok: побайтово идентичные ключи и список форматов что с
  флагом, что без). Поэтому `core.resolve_video_or_playlist(url)` объединяет
  оба вызова: делает `detect_playlist()`, и если это не плейлист **и** в
  ответе уже есть непустой `formats` — отдаёт его как есть, без второго
  вызова `run_ytdlp_json_ex()`; если `formats` вдруг нет (нетипичный
  экстрактор — на этот случай в лог пишется `len(formats)` для мониторинга)
  — довыполняет полный запрос, как раньше. Все три инструмента
  (`youtube.py`/`compress.py`/`trim.py`) используют именно
  `resolve_video_or_playlist()`, а не `detect_playlist()` +
  `run_ytdlp_json_ex()` по отдельности; «сжать» и «нарезать» на плейлист
  по-прежнему отвечают понятной ошибкой — полноценная поддержка плейлистов
  есть только в «скачать». Время каждого шага и число реально сделанных
  попыток/вызовов логируются в миллисекундах (`detect_playlist`,
  `run_ytdlp_json_ex`, `resolve_video_or_playlist`) — по логу видно, сколько
  подряд вызовов yt-dlp ушло на конкретный запрос.
- **Обёртки ffmpeg/ffprobe** — `ffprobe_duration()`, `ffprobe_resolution()`,
  `run_ffmpeg_progress()` (запускает ffmpeg с машинным `-progress` и обновляет
  `job['progress']`; поддерживает диапазон `base/span` для двухпроходного
  кодирования и уважает отмену). Все три вызывают резолвнутые `FFMPEG_BIN`/
  `FFPROBE_BIN` (см. «Резолвинг внешних зависимостей» выше), не голые строки.
- **Уборщик (`start_janitor`)** — фоновый поток: при старте чистит остатки
  прошлых запусков в `DOWNLOADS_DIR`, затем каждые 15 с подчищает отлежавшиеся
  задачи (см. ниже «Хранение и авто-очистка») и старый кэш. Удаляются ТОЛЬКО
  каталоги, созданные приложением (job_id, `ytdlp-update-*`) — если temp/cache
  указывают на постороннюю папку, её содержимое уборщик не трогает
  (`is_app_job_dir`/`is_cache_dir`).
- **Хелперы для страницы настроек** — `path_stats(path)` (размер, mtime, atime
  для файла/папки) и `clear_path(path)` (очистка содержимого).
- Все дочерние процессы на Windows запускаются с `CREATE_NO_WINDOW`, чтобы не
  мигало консольное окно.

### `app.py` — сервер

Регистрирует blueprint'ы всех инструментов (`tools.blueprints()`) + отдельно
blueprint настроек (`tools.settings.bp`, не входит в `tools.ALL`, поэтому не
становится плиткой на лендинге). Отдаёт лендинг и **общие** роуты задач:

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET  | `/api/status/<job_id>` | прогресс/статус задачи |
| POST | `/api/cancel/<job_id>` | отменить задачу (терминирует процесс) |
| GET  | `/api/file/<job_id>`   | скачать готовый файл в браузер |
| GET  | `/api/deps/info` | статус/ссылки/команды по группам зависимостей (yt-dlp, ffmpeg+ffprobe, Deno) — для окна установки и настроек |
| POST | `/api/deps/install` | `{targets: [...]}` → запуск скачивания недостающих зависимостей в `bin/` (та же система задач `JOBS` — прогресс/отмена через роуты выше) |

Роуты установки зависимостей — общие (не в `tools/`), потому что окно
установки открывается с любой страницы инструмента и со страницы настроек
одинаково (см. «Установка и обновление зависимостей» ниже).

Инструмент-специфичные роуты (например, `/youtube/api/info`,
`/compress/api/upload`, `/trim/api/start`, `/settings/api/save`) живут в
blueprint'е самого инструмента — таблицы ниже.

State-changing POST-запросы защищены от чужих сайтов: `before_request` в
`app.py` отклоняет запрос с `Sec-Fetch-Site: cross-site`, с посторонним
`Origin` или `Host` (allowlist `127.0.0.1`/`localhost`/`::1` + `YTD_HOST`).
Это закрывает CSRF на `/api/quit`, `/settings/api/reset` и DNS-rebinding;
клиенты без этих заголовков (curl) не блокируются. Ссылки принимаются только
`http(s)://`, а в команду yt-dlp URL передаётся после `--`, чтобы строка вида
`--exec=...` не была исполнена как опция yt-dlp.

### Инструмент = модуль в `tools/`

Каждый модуль экспортирует две вещи:

- `bp` — Flask `Blueprint` со своим `url_prefix` и роутами (страница + API);
- `TOOL` — метаданные для лендинга/сайдбара:
  `{id, name, desc, icon (строка SVG), url}`.

И регистрируется одной строкой в `tools/__init__.py` (`ALL = [...]`).
**Настройки — исключение**: у них есть `TOOL` (для навигации), но модуль не
входит в `ALL`, а регистрируется напрямую в `app.py`, чтобы не попасть в
плитки лендинга.

## Как добавить новый инструмент

1. Создайте `tools/myтул.py`:
   ```python
   from flask import Blueprint, render_template
   import core

   bp = Blueprint("mytool", __name__, url_prefix="/mytool")

   TOOL = {
       "id": "mytool",
       "name": "мой инструмент",
       "desc": "что он делает",
       "url": "/mytool/",
       "icon": '<svg viewBox="0 0 24 24"><path d="..."/></svg>',
   }

   @bp.route("/")
   def page():
       return render_template("mytool.html")

   # ... свои /api/* роуты; для долгих операций заводите задачу через core.new_job()
   #     и обновляйте её прогресс из фонового потока (см. youtube.py / compress.py / trim.py)
   ```
2. Создайте `templates/mytool.html` (наследует `_base.html` — стили,
   Lucide-иконки и навигация подтянутся сами).
3. Впишите модуль в `tools/__init__.py`:
   ```python
   from . import youtube, compress, trim, mytool
   ALL = [youtube, compress, trim, mytool]
   ```

Всё. Плитка на лендинге, пункт в сайдбаре и общие роуты задач появятся
автоматически.

## Инструмент «скачать» (`tools/youtube.py`)

| Метод | Путь | `{payload}` → ответ |
|-------|------|------|
| POST | `/youtube/api/info` | `{url}` → `{job_id, pending: true}`: получение метаданных уходит в фон (см. п.1), фронт опрашивает `/api/status/<job_id>` и забирает результат |
| GET  | `/youtube/api/info_result/<job_id>` | метаданные одиночного видео **или**, если ссылка на плейлист, `{is_playlist: true, playlist}`; `202`, пока задача не готова |
| GET  | `/youtube/api/formats` | список форматов видео/аудио для UI |
| POST | `/youtube/api/download` | `{url, job_id, mode, height, audio_id, video_format, audio_format}` → запуск скачивания одного видео |
| POST | `/youtube/api/download_playlist` | `{job_id, mode, height, audio_id, video_format, audio_format, selected_ids, delivery}` → запуск скачивания отмеченных видео плейлиста |
| GET  | `/youtube/api/playlist_status/<job_id>` | агрегированный статус плейлиста + статус каждого отдельного видео одним запросом |

Режимы: видео+звук / только видео / только звук. Перед реальным скачиванием
проверяется кэш (`core.cache_get`) по ключу `video_id + параметры` — повтор той
же связки качество/формат не скачивается заново.

### Плейлисты

`/api/info` определяет тип ссылки через `core.resolve_video_or_playlist()`
(внутри — `detect_playlist()`, без вытягивания полных форматов каждого
дочернего видео плейлиста — иначе это упирается в тот же 120-секундный
таймаут, от которого специально уходили). Для одиночного видео второй,
отдельный запрос полных метаданных в норме не делается вовсе — см. «Общая
инфраструктура» → «Метаданные yt-dlp» выше.

- **Интерфейс** (`templates/youtube.html`) — двухколоночная карточка: слева
  обложка/название/канал плейлиста, справа прокручиваемый список видео
  (чекбокс + превью + название + канал + длительность), все отмечены по
  умолчанию. Кнопка «выделить все» / «убрать выделения» (подпись зависит от
  текущего состояния выбора) переключает разом все чекбоксы.
- **Настройки общие на весь плейлист** — «что скачать» и «качество
  видео/формат» выбираются один раз и применяются к каждому отмеченному
  видео. Качество берётся из фиксированного набора высот (`PLAYLIST_HEIGHTS`
  в `tools/youtube.py`, приходит с сервера в поле `playlist.heights`), а не
  из фактических форматов каждого ролика — они намеренно не вытягиваются
  (см. выше). По той же причине для плейлиста нет выбора конкретной
  аудиодорожки по id — только формат/авто.
- **Реализация** — `N` независимых задач `core.JOBS` (по одной на видео,
  переиспользуют весь существующий прогресс/отмену/кэш), а не одна команда
  yt-dlp на весь плейлист. Оркестратор-поток (`_download_playlist_thread`)
  качает их последовательно и обновляет агрегированный прогресс
  родительской задачи (`done_count`/`total_count`/`stage`, например «3 из 12
  скачано»).
- **Способ доставки** — сегментированный переключатель над кнопкой
  «скачать»:
  - **«скачать в .zip»** (по умолчанию) — когда все отмеченные видео
    скачаны, успешные упаковываются в один архив
    `{название плейлиста} [{N} ep].zip` (`N` — фактическое количество
    успешно скачанных, не количество отмеченных) и отдаются через
    `/api/file/<job_id>` как обычно. Ошибка на отдельном видео не роняет
    процесс — архив собирается из того, что скачалось, остальные видео
    отмечаются в интерфейсе с текстом ошибки.
  - **«потоковая загрузка»** — каждое видео уходит в браузер сразу по
    готовности (`/api/file/<job_id>` конкретной дочерней задачи), не
    дожидаясь остальных.
- **Отмена — «мягкая»**: `POST /api/cancel/<job_id>` останавливает только
  постановку **следующих** видео в очередь — уже начатое скачивание
  доигрывает до конца (подпроцесс не прерывается). Фронт не глушит опрос
  статуса сразу по клику: он продолжает опрашивать
  `/api/playlist_status/<job_id>`, пока родительская задача **и** каждое
  отдельное видео не дойдут до финального статуса — иначе прогресс ещё
  докачивающегося видео замер бы на старом значении.

## Инструмент «сжать» (`tools/compress.py`)

| Метод | Путь | `{payload}` → ответ |
|-------|------|------|
| POST | `/compress/api/upload` | файл (multipart) → `job_id`, длительность, исходная высота |
| POST | `/compress/api/fetch` | `{url}` → метаданные YouTube + `video_id` |
| POST | `/compress/api/start` | `{job_id, target_mb, audio_kbps, height}` → запуск двухпроходного сжатия |

Целевой битрейт считается из `target_mb` и длительности (запас 3% на
накладные расходы контейнера). YouTube-исходник для сжатия тоже кэшируется
(`video_id|compress-src`).

**`target_mb = 0`** — особый случай: сжатие без привязки к размеру файла,
только по выбранным разрешению и битрейту звука (пресет «0» рядом с полем,
и подсказка под ним прямо на странице). В этом режиме `_compress_thread`
идёт другим путём: однопроходный CRF-энкод (`-crf 20 -preset medium`) вместо
двухпроходного побитрейтного — двухпроходность нужна именно ради точного
попадания в размер, а раз цели по размеру нет, в ней смысла нет. Имя файла
без суффикса `[XMB]` — просто `[Nп]`, если выбрано конкретное разрешение,
либо вообще без суффикса при «исходном».

Ссылка на плейлист отклоняется понятной ошибкой уже на `/api/fetch`
(`core.resolve_video_or_playlist()`) — «сжать» работает только с одним
видео, плейлисты целиком поддерживает только «скачать».

## Инструмент «нарезать» (`tools/trim.py`)

Самый функционально насыщенный модуль. Полный цикл: источник → подготовка
(скачивание/анализ) → редактор (волна + видеоряд) → нарезка (+опционально
сжатие) → результат.

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET  | `/trim/api/formats` | список аудио/видео форматов вывода |
| POST | `/trim/api/upload` | файл (multipart) → `job_id`, фоновый анализ запускается сразу |
| POST | `/trim/api/info` | `{url}` → метаданные YouTube без скачивания (длительность, доступные высоты, `video_id`) |
| POST | `/trim/api/prepare` | `{job_id, height}` → скачать ролик во временную папку (или взять из кэша) и проанализировать |
| GET  | `/trim/api/data/<job_id>` | волна, видео/аудио-флаги, fps, список аудиодорожек, разрешение |
| GET  | `/trim/api/media/<job_id>?a=<idx>` | исходник для плеера; `a=<idx>` — версия с конкретной аудиодорожкой (ремукс без перекодирования, кэшируется на диске) |
| GET  | `/trim/api/peaks/<job_id>?a=<idx>` | волна именно выбранной аудиодорожки (для синхронной смены звука+волны) |
| GET  | `/trim/api/filmstrip/<job_id>?a=&b=&n=` | полоса из `n` кадров для видимого участка `[a,b]` (под текущий зум), кэш на диске |
| POST | `/trim/api/start` | `{job_id, start, end, mode, format, audio, compress, target_mb, resolution, audio_kbps}` → запуск нарезки |
| GET  | `/trim/api/result/<job_id>` | скачать готовый фрагмент (без форсированной уборки оригинала — можно нарезать ещё) |

Ключевые детали реализации:

- **Таймкод из ссылки → маркер начала фрагмента** — полностью на клиенте
  (`parseTimestampFromUrl()` в `templates/trim.html`), backend не участвует.
  Распознаётся при получении ссылки (`/api/info`), специфично для YouTube:
  `?t=95`, `?t=1m35s`, `&start=95` (embed-ссылки), `#t=1m35s` (fragment,
  разбирается отдельно от query-параметров). У других сайтов, поддерживаемых
  yt-dlp, единого стандарта таймкода в ссылке нет — функция просто возвращает
  `null`, маркер остаётся на 0, как раньше; обычная загрузка локального файла
  таймкод тоже не трогает. Если таймкод распознан — маркер начала (`ed.start`)
  ставится на него (клампится в `[0, длительность]` — битая/не та ссылка не
  ломает редактор), а под полями таймингов показывается «таймкод определён:
  M:SS». Маркер конца зависит от настройки «длина фрагмента по умолчанию для
  ссылки с таймкодом» (раздел «Настройки» ниже): пусто — как раньше, на всю
  длительность; задано число N секунд — `ed.end = start + N` (тоже в границах
  видео). Настройка применяется **только** когда таймкод реально распознан из
  вставленной ссылки.
- **Плейлисты не поддерживаются** — ссылка на плейлист отклоняется понятной
  ошибкой уже на `/api/info` (`core.resolve_video_or_playlist()`); нарезать
  можно только одно видео/файл, плейлисты целиком — только через «скачать».
- **Видеоряд** строится **по запросу под зум**, а не один раз на весь ролик:
  при приближении (debounce ~220 мс) фронт запрашивает свежую полосу из 80
  кадров именно для видимого диапазона — иначе на длинном видео при зуме
  получались повторяющиеся кадры. Кадры рисуются на canvas в натуральных
  пропорциях (16:9, дополнительно сжаты ×2 по горизонтали), а не растянутой
  картинкой.
- **Зум колёсиком** (как в FL Studio) — вокруг курсора, двойной клик
  возвращает к полному треку.
- **Тайминги**: поля ввода + перетаскиваемые ручки + кнопки-степперы под
  полями (`-1s`/`+1s` — ±1 секунда, `-1f`/`+1f` — ±1 кадр; для аудио шаг
  кадра нет, используется 0.1 с — см. `frameStep()`). Формат поля и подписей
  на волне — `ММ:СС.ммм (Nf)`: полные миллисекунды и текущий кадр в скобках
  (кадр считается от `fps` ролика, `Math.floor((s % 1) * fps)`; для аудио
  без видео кадра нет — суффикс `(Nf)` не показывается). Длительность видео и
  выбранного фрагмента показываются отдельно, в десятых долях секунды, без
  номера кадра — там нет позиции, к которой кадр можно отнести. Любое
  изменение границы запускает короткое прослушивание фрагмента (как при
  перетаскивании).
- **Пробел** — play/pause (не срабатывает при фокусе на полях/кнопках).
- **Аудиодорожки**: если их несколько, в шапке редактора (справа от названия)
  появляется селектор «Аудиодорожка №X - название». Смена дорожки переключает
  **и звук плеера, и волну** (через `?a=<idx>` на `/api/media` и `/api/peaks`),
  и пробрасывается в финальный рез (`-map 0:a:<idx>`).
- **Микро-fade** (~12 мс) на краях реза — убирает щелчки от обрыва волны на
  произвольной фазе. Раньше был режим «как в оригинале» (`-c copy`), но его
  убрали именно из-за невозможности наложить fade без перекодирования —
  сейчас экспорт всегда перекодирует.
- **Опциональное сжатие** — чекбокс «сжать» между «что сохранить» и
  «форматом» (виден только в режиме «видео»). Без галочки — обычная нарезка;
  с галочкой — раскрывается то же меню сжатия, что у инструмента «сжать»
  (целевой размер/разрешение/битрейт звука), кнопка становится
  «сжать + обрезать», нарезка идёт двухпроходным x264 под целевой размер.
- **Имя итогового файла** строится из `core.safe_filename(src.stem)`
  (`core.py`) — **не** из `werkzeug.utils.secure_filename`. Werkzeug стирает
  вообще все не-ASCII символы, поэтому названия видео на русском/любом
  нелатинском языке превращались в пустую строку и итоговый файл получал
  общее имя `media`/`video` вместо настоящего названия. `core.safe_filename`
  убирает только реально недопустимые в путях Windows символы
  (`<>:"/\|?*` и управляющие), сохраняя кириллицу и любой юникод. Та же
  функция используется в `tools/compress.py` для имени загружаемого локально
  файла — по той же причине.

## Хранение и авто-очистка `temp/`

Рабочие файлы каждой задачи лежат в `temp/<job_id>/` (по умолчанию рядом с
exe — портабельность, см. `core.default_temp_dir()` — либо там, куда
указывают настройки, см. ниже). Это **временное** хранилище: браузер всё
равно скачивает результат себе, поэтому копию держать незачем. За уборкой
следит фоновый уборщик (`core.start_janitor`):

- **После отдачи файла в браузер** папка задачи удаляется через
  `CLEANUP_AFTER_SERVE` секунд (по умолчанию 30 — запас на повторное скачивание).
- **Завершённые, но так и не скачанные** задачи убираются через
  `CLEANUP_IDLE_DONE` (10 мин).
- **Брошенные** задачи (например, загруженный, но не сжатый файл) — через
  `CLEANUP_IDLE_STALE` (30 мин).
- **При старте** остатки прошлых запусков (после краша/убийства процесса) в
  `temp/` удаляются сразу — но только каталоги со «своими» именами (job_id /
  `ytdlp-update-*`, см. `core.is_app_job_dir`). Кэш чистится аналогично, только
  по именам `core.is_cache_dir`.
- Активные задачи (идёт скачивание/сжатие/нарезка) уборщик не трогает.
- **Кэш роликов** — отдельная папка `cache/` (по умолчанию тоже рядом с exe,
  см. `core.default_cache_dir()`), живёт по своему TTL (6 ч с последнего
  обращения) — см. «Кэш скачанных роликов» выше; обычный уборщик задач её не
  трогает.

## Пути: три режима и фоллбэк

Пути режимов «в системе»/«свой путь» абсолютны и могут стать недоступны
(диск отключили, папку удалили) — проверяется при каждом применении настроек
(`core.apply_settings()` → `_dir_available()`, дешёвая проверка `os.access`
без обхода файловой системы: идёт вверх по дереву до ближайшего
существующего предка и проверяет его на запись — недоступно, если дошли до
несуществующего корня диска). **temp и cache обрабатываются по-разному**:

- **temp недоступен** (обязателен для операций — скачивание/сжатие/нарезка
  пишут прямо в него) — блокирует: `core.TEMP_AVAILABLE = False`,
  `core.temp_blocked_error()` возвращает понятную ошибку, которую проверяют
  все API-роуты, пишущие файлы (`upload`/`download`/`start`/`prepare` во всех
  трёх инструментах, ДО начала операции — тот же паттерн, что у
  `missing_dependencies_payload()` из этапа 1). `DOWNLOADS_DIR` при этом
  всё равно откатывается на режим «в папке приложения» (иначе `core.JOBS`
  писать некуда и приложение просто упадёт) — но это **не считается
  исправлением**: `TEMP_AVAILABLE` остаётся `False`, настройка `temp_mode`
  не трогается молча, операции остаются заблокированы, пока пользователь не
  подтвердит переключение явно.
- **cache недоступен** (опционален — только ускорение повторных скачиваний)
  — НЕ блокирует ничего: `core.CACHE_AVAILABLE = False` просто выключает
  `cache_get()`/`cache_put()` (оба возвращают пусто/оригинал без попытки
  писать в недоступную папку) — приложение работает, просто без
  переиспользования уже скачанных роликов.

### На главной странице (`/`)

`GET /api/paths_status` дёргается при каждом открытии главной (наряду с
`/api/disk_check`, `/api/ytdlp_update_check`):

- **Постоянный баннер** сверху (`#pathsWarning`, тот же стиль, что у
  предупреждения о месте на диске) — пока недоступен хоть один из temp/cache,
  с текстом, называющим именно то, что сломано («temp», «cache» или «temp и
  cache»); клик — переход в настройки.
- **temp недоступен → блокирующая модалка** (`#tempUnavailableModal`) —
  единственная модалка в приложении без крестика/клика-по-фону: только два
  продуктивных выхода, «глухая отмена» заперла бы пользователя, не подсказав,
  что делать. «Да, использовать папку приложения» реально сохраняет
  `temp_mode: "app"` (`POST /settings/api/save`) и закрывает модалку без
  перезагрузки; «Открыть настройки» — переход на страницу настроек чинить
  вручную (свой путь или системный режим).
- **cache недоступен → мягкий тост** (`#cacheToast`, тот же паттерн, что у
  уведомления об обновлении yt-dlp, только повыше — оба тоста может быть
  видно одновременно) — просто закрывается крестиком, ничего не блокирует.

### На странице настроек

Пульсация невалидной строки (`.path-row.path-invalid`, CSS-анимация
`box-shadow`, без JS-таймеров):

- держится, пока путь невалиден;
- замирает под курсором (`:hover` → `animation-play-state: paused`) — не
  мельтешит, пока пользователь работает со строкой;
- возобновляется, если курсор убран, а проблема не решена (обычное
  поведение `:hover`, ничего специально поддерживать не нужно);
- гаснет насовсем, когда путь стал валиден — класс снимается в JS
  (`renderPathRow()`), не таймером: привязано к реальной починке, а не к
  выходу мыши.

Строки temp/cache на странице настроек досверяются раз в 5 секунд
(`pollPathsStatus()`, `GET /api/paths_status`) — если пользователь
переподключит диск прямо во время работы со страницей, пульсация погаснет
без сохранения/перезагрузки.

## Настройки (`/settings/`, `tools/settings.py`)

Отдельная страница, иконка-шестерёнка в самом низу левой панели навигации (с
разделителем от остальных пунктов). **Все изменения сохраняются автоматически**
при изменении поля — кнопки «Сохранить» нет. Хранится в `settings.json` рядом
с приложением; применяется через `core.save_settings()` → `core.apply_settings()`.

### Раздел 1 — предпочтения скачивания
- Расширение видео-файла (оригинал/MP4/MOV/WEBM/MKV), расширение аудио-файла
  (MP3/WAV/AAC/Opus). Разрешение видео здесь не настраивается — только на
  самой странице «скачать» (селектор качества); глобального предпочтения по
  разрешению в приложении нет (было — не применялось нигде в логике
  скачивания, убрано как мёртвая настройка).
- «Встраивать обложку и метаданные» (чекбокс `embed_metadata`, по умолчанию
  вкл) — применяется в «скачать» (`tools/youtube.py`) и «нарезать»
  (`tools/trim.py`) к любому результату, полученному по ссылке (для локально
  загруженных в «нарезать» файлов не применяется — метаданных для них нет):
  - **видео** (MP4/MKV) — только метаданные (название, канал/автор), через
    `--embed-metadata` yt-dlp в «скачать» или `-metadata` ffmpeg в «нарезать».
    Обложка в видео **не встраивается** — плохо поддерживается плеерами и
    форматом WebM, поэтому для WebM метаданные тоже не трогаются.
  - **аудио** — метаданные и обложка вместе: полноценно для MP3/M4A, best-effort
    для Opus (контейнер поддерживает встраивание хуже). Для
    **WAV не применяется вовсе** (формат не поддерживает встраивание) — ни
    метаданные, ни обложка.
  - Метаданные берутся из уже полученной при `/api/info` информации о видео
    (title/uploader) — отдельный запрос к yt-dlp только ради метаданных не
    делается. В «нарезать» обложка (по ссылке на неё) скачивается один раз и
    приводится к JPEG через Pillow (`tools/trim.py: _fetch_cover`) — это
    делает встраивание надёжным независимо от исходного формата картинки
    (webp/png/…). Если встраивание обложки всё же ломает экспорт (актуально
    для best-effort Opus) — «нарезать» автоматически повторяет экспорт без
    неё, а не проваливает всю нарезку.
- Битрейт аудио при сжатии (128/192/256/320 кбит/с) и целевой размер сжатия по
  умолчанию в МБ (пусто — без принудительного сжатия по размеру).
- Длина фрагмента по умолчанию для ссылки с таймкодом, в секундах (пусто —
  маркер конца на всей длительности видео). Влияет только на «нарезать» и
  только когда таймкод реально распознан из вставленной ссылки — см. «Ключевые
  детали реализации» инструмента «нарезать» выше. Значение должно быть больше
  0 — проверяется и на фронте (`min="1"`), и на бэкенде
  (`core._normalize_clip_length`, тот же паттерн тихой нормализации
  недопустимых значений, что у `compress_audio_kbps`/`theme`/режимов путей).
- Ограничение скорости скачивания: число + единица (КБ/с, МБ/с, КБит/с,
  МБит/с). Биты пересчитываются в байты перед передачей в `--limit-rate`
  yt-dlp (см. `core._rate_limit_arg`).
- «Лимит одновременных загрузок» (плейлист) — 1/2/3/5/без ограничений,
  по умолчанию **3**. Рядом — постоянное предупреждение (видно при любом
  выбранном значении, не только «без ограничений»): большое число
  одновременных загрузок или отключённый лимит может привести к временной
  блокировке IP или самого YouTube-аккаунта, чьи cookies используются. При
  выборе именно «без ограничений» дополнительно показывается модалка
  подтверждения с тем же текстом; при отмене список возвращается к
  предыдущему подтверждённому значению (или к дефолту **3**, если предыдущего
  ещё не было) — остальные значения применяются сразу, без подтверждения.
  Лимит фиксируется в момент **запуска** скачивания плейлиста
  (`tools/youtube.py: api_download_playlist` читает настройку один раз и
  передаёт её в `_download_playlist_thread`) — изменение настройки не влияет
  на уже выполняющуюся задачу, только на следующий запуск. Реализовано через
  `threading.Semaphore(limit)`: оркестратор занимает слот перед стартом
  каждого дочернего видео и освобождает его по завершении — «без ограничений»
  просто пропускает семафор, и все отмеченные видео стартуют сразу. Прогресс
  «N из M» и способ доставки (zip/потоково) работают одинаково при любом
  лимите — это лишь про то, сколько видео скачивается одновременно.
- Тема: «Тёмная/Светлая» — переключается мгновенно и сразу на всех страницах,
  без перезагрузки (`data-theme` на `<html>`, см. «Дизайн» → «Тема» ниже).

### Раздел 2 — пути
- **Папка временных файлов и папка кэша** — независимые строки, три режима
  каждая (дропдаун 2/8 ширины · поле пути 4/8 · кнопка 2/8):
  1. **«в папке приложения»** (дефолт) — `<папка exe>/temp` или `/cache`
     (`core.default_temp_dir()`/`default_cache_dir()`);
  2. **«в системе»** — системный temp / `%LOCALAPPDATA%\jade.tools\cache`
     (`core.system_temp_dir()`/`system_cache_dir()`);
  3. **«свой путь»** — произвольная папка, выбирается кнопкой «обзор…».

  Поле пути показывает реальный путь во **всех трёх** режимах, но
  редактируется только в «свой путь» (в 1–2 оно readonly — путь вычисляется
  сам). Кнопка меняет и подпись, и действие: в режимах 1–2 это **«открыть»**
  (создаёт папку, если её ещё нет, и открывает в проводнике —
  `POST /settings/api/open_path`), в режиме 3 — **«обзор…»** (диалог выбора
  папки). Хранение — режим и путь раздельно: `temp_mode`+`temp_custom_path`,
  `cache_mode`+`cache_custom_path` (`core.DEFAULT_SETTINGS`); настройки,
  сохранённые до этого разделения (одна строка `temp_path`/`cache_path`, ""
  = системный дефолт), мигрируют автоматически при первой загрузке —
  пустое значение уходит в новый дефолт **«в папке приложения»** (не в
  «в системе», как вело себя старое пустое значение фактически), уже
  заданный пользователем путь сохраняется как режим «свой путь». Подробности
  резолвинга и фоллбэка при недоступном пути — раздел «Пути: три режима и
  фоллбэк» ниже.
- «Использовать cookies» (главный чекбокс, **по умолчанию выкл**) — выключен
  → блока ниже нет вовсе, cookies не подключаются никогда. Включён →
  вложенный тумблер «подтягивать автоматически из браузера» (по умолчанию
  вкл при раскрытии): включён — дропдаун браузера (**только Firefox и форки**
  — LibreWolf, Waterfox, Zen, никаких Chromium); снят — путь к своему
  `cookies.txt` + раскрывающаяся инструкция экспорта, рядом дата изменения
  файла (напоминание, что куки устаревают; режим «из браузера» этой проблеме
  не подвержен — куки читаются заново при каждом скачивании). Даже когда
  cookies включены, они подключаются не всегда, а только когда без них не
  получилось — см. «Cookies и доступ к YouTube».
- Главный/вложенный чекбоксы и зависимые блоки реализованы единым
  переиспользуемым паттерном на странице (см. `refreshToggles()` в
  `settings.html`).
- Поле пути и путь к файлу куки валидируются на сервере: несуществующая папка
  или файл не `.txt` — отклоняются с понятной ошибкой, сохранение не проходит
  (`tools/settings.py: _validate`).
- Кнопки «обзор…» открывают нативный диалог выбора (tkinter в отдельном
  потоке, `tools/settings.py: _pick`) — поэтому `tkinter` **не исключён** из
  сборки (см. `jade.spec`).

### Раздел 3 — файлы
Кэш и временные файлы — кнопка «очистить» (`POST /settings/api/clear`), у
каждой строки размер, дата последнего изменения и дата последнего обращения
(`core.path_stats`). Куки — кнопка **«показать»**, не «очистить»: cookies.txt
не удаляется этой страницей, кнопка лишь открывает системный проводник с
выделенным файлом (`POST /settings/api/open_path` с `target: "cookies"`, тот
же паттерн `explorer /select,<файл>`, что и у «показать файл логов» в разделе
«журнал» ниже). Путь резолвится `core.resolve_cookies_file()`: явно заданный
в настройках `cookies_file_path`, если существует, иначе дефолтный
`cookies.txt` рядом с приложением — независимо от того, включены ли cookies
сейчас (в отличие от `YT_COOKIES_FILE`, которая пуста при выключенной
настройке). Если файла нет — кнопка неактивна, строка показывает «файл куки
не используется или не найден»; проводник в пустоту не открывается.

### Раздел 4 — журнал
**Лог работы приложения** — размер и даты (см. «Логирование» ниже), кнопка
«показать файл логов» открывает системный проводник с выделенным файлом
(не открывает файл внутри приложения).

### Раздел 5 — зависимости
Три строки — статус/расположение каждой зависимости
(`core.dependency_groups()`/`ytdlp_source_kind()`) и действие:

- **yt-dlp** — расположение («в папке приложения (bin/)» / «в системе (pip)»
  / «в системе (другой способ)» / «не найдено») + кнопка «проверить
  обновление» → ручная проверка версии, результат («обновлён» / «доступна
  новая версия X» / ошибка) добавляется к расположению через « · ». Кнопка
  неактивна («обновите вручную» / «не найден»), если источник не `bin`/`pip`
  — см. «Установка и обновление зависимостей» → «Обновление yt-dlp — по
  источнику». Автоматическая фоновая проверка при открытии главной страницы
  — отдельный механизм, не связанный с этой кнопкой (она всегда форсирует
  свежий запрос).
- **ffmpeg / ffprobe** и **Deno** — только расположение + кнопка
  «переустановить» (открывает окно установки заново, без своей логики
  обновления версий — см. «ffmpeg / Deno — без автообновления»).

### Сброс и версия
Кнопка «сбросить настройки» (красный текст) — открывает модалку с явным
предупреждением о необратимости, сброс только после подтверждения
(`core.reset_settings()`). Под кнопкой — подпись текущей версии.

> Модалка подтверждения — **общий переиспользуемый компонент**
> (`#confirmModal` + `showConfirm({title, text, okText, cancelText, onConfirm,
> onCancel})` в `settings.html`), не завязанный на текст про сброс: заголовок,
> текст и подписи кнопок передаются параметрами. Второй сценарий, где он
> используется — подтверждение выбора «без ограничений» в лимите
> одновременных загрузок (см. «Раздел 1» выше).

> **Константа версии приложения** — `VERSION_NUMBER` в
> [`tools/settings.py`](tools/settings.py) (формат `x.ddmmyy`: x — номер
> релиза на GitHub, ddmmyy — дата изменений и/или публикации:
> день/месяц/две цифры года; например `"0.040726"`).
> Показанная в интерфейсе строка `VERSION` собирается из неё же
> (`f"{VERSION_NUMBER} - jade.tools by Gwendarr"`). Значение статичное,
> обновляется вручную при релизах — НЕ вычисляется от системной даты.

## Логирование

Приложение ведёт лог работы в отдельный файл — **не** внутри `downloads/`
или кэша, чтобы очистка этих папок (кнопки на странице настроек) не задевала
лог. Реализация — `core.py`, модуль `logging` + `RotatingFileHandler`:

- **Файл:** `%LOCALAPPDATA%\jade.tools\logs\jade.log` (`core.LOG_FILE`,
  папка — `core.LOG_DIR` / `core.default_log_dir()`).
- **Ротация:** до 3 файлов по 2 МБ (`jade.log`, `jade.log.1`, `jade.log.2`) —
  логи не растут бесконечно.
- **Что пишется:** старт/остановка сервера, изменения и сброс настроек,
  начало/успех/ошибка каждой фоновой задачи во всех трёх инструментах
  (скачивание, сжатие, нарезка), попадания и промахи кэша скачанных роликов,
  ошибки yt-dlp (централизованно — через `friendly_ytdlp_error`, который
  логирует сырой `stderr` при любом вызове из любого инструмента) и ffmpeg
  (ненулевой код возврата), действия уборщика (сколько остатков удалено при
  старте), результаты проверки обновления yt-dlp и срабатывания
  предупреждения о месте на диске.
- **Просмотр:** страница настроек → раздел «журнал и обновления» → кнопка
  **«показать файл логов»** — открывает системный проводник (`explorer
  /select,<путь>`) с выделенным файлом. Файл **не открывается внутри
  приложения** — только показывается его расположение
  (`tools/settings.py: api_reveal_log`).

## Установка и обновление зависимостей

### Окно установки

Когда какому-то инструменту не хватает зависимости (`core.missing_dependencies_payload()`
вернул `need_install: true`) — фронт открывает общее окно установки
(`templates/_base.html: window.openInstallModal()`, тот же паттерн веб-модалки,
что у подтверждения сброса настроек). Окно ничего не решает само — только
показывает варианты, действие только после явного выбора пользователя (не
блокирует принудительно, закрывается крестиком/фоном):

1. **Скачать автоматически в `bin/`** — `POST /api/deps/install`
   (`core.start_install_job()`) качает недостающее с GitHub Releases
   **последовательно** (yt-dlp → Deno → ffmpeg — от лёгкого к тяжёлому) через
   ту же систему задач `JOBS`, что и скачивание видео: прогресс и отмена — те
   же `/api/status/<job_id>` и `/api/cancel/<job_id>`, без отдельной
   реализации. Источники (`core._RELEASE_REPOS`): `yt-dlp/yt-dlp` (файл
   `yt-dlp.exe` целиком), `BtbN/FFmpeg-Builds` (ассет строго
   `ffmpeg-master-latest-win64-gpl.zip`, БЕЗ суффикса `-shared` — та сборка
   требует сопутствующие `av*.dll`), `denoland/deno`
   (`deno-x86_64-pc-windows-msvc.zip`). Для zip-архивов —
   `core._extract_zip_members()` достаёт ТОЛЬКО нужные файлы (`ffmpeg.exe`+
   `ffprobe.exe` из общего архива ffmpeg, `deno.exe` из архива Deno) по имени
   файла независимо от пути внутри архива, без полной распаковки (экономия
   места и времени — полный ffmpeg-архив содержит документацию, `ffplay.exe`
   и т.д.). Каждый файл сначала пишется как `<имя>.part` и переименовывается
   в финальное имя только после полного копирования — обрыв не портит уже
   рабочий бинарник. Предупреждение об объёме — «до ~540 МБ временно, ~335 МБ
   после» (числа с реального замера, могут немного плавать — сборки `master`
   меняются).
2. **Скачать вручную с GitHub** — те же ссылки на релизы + путь до `bin/`
   (`core.BIN_DIR`), без автоматизации — пользователь сам кладёт файлы и
   перезапускает приложение.
3. **pip / winget** — готовые команды с кнопкой «копировать» (yt-dlp — `pip
   install -U yt-dlp`, ffmpeg/Deno — `winget install -e --id ...`), у каждой
   есть фоллбэк-ссылка на GitHub. Приложение сами команды **не выполняет**
   (winget может требовать UAC, pip — Python) — только показывает.

Backend-часть этих трёх вариантов — `GET /api/deps/info` (статус/ссылки/
команды по группам `core.DEP_GROUPS`: `yt-dlp`, `ffmpeg`+`ffprobe` одним
пунктом — общий релиз, `deno`) и `POST /api/deps/install`.

### Обновление yt-dlp — по источнику

YouTube часто меняет защиту, поэтому устаревший `yt-dlp` — частая причина
поломок скачивания (см. «Cookies и доступ к YouTube»). В отличие от ffmpeg/
Deno (стабильные бинарники — для них в настройках только статус и
«переустановить», без проверки версий), yt-dlp меняется часто и умеет
самообновляться, поэтому у него отдельная система:

- **Определение источника** (`core.ytdlp_source_kind()`) — определяет, ЧЕМ и
  можно ли вообще обновлять:
  - `"bin"` — копия в `bin/` рядом с exe → приложение обновляет само:
    сначала пробует встроенный self-update (`yt-dlp -U`), при неудаче —
    перекачивает `yt-dlp.exe` заново с GitHub Releases (`core._install_ytdlp`,
    та же функция, что и при первичной установке).
  - `"pip"` — резолвится через системный `PATH`, и `pip show yt-dlp`
    подтверждает pip-происхождение → `pip install --upgrade yt-dlp` (лаунчер
    `py -3`, фоллбэк `python`) — путь, работавший до появления bin/-варианта,
    не изменён.
  - `"system-other"` — в `PATH`, но `pip show` его не видит (winget, ручной
    exe) → приложение НЕ трогает; кнопка обновления в настройках неактивна,
    подпись «обновите вручную».
  
  Единственная проверка, различающая `"pip"`/`"system-other"` — `pip show
  yt-dlp`; winget отдельно не распознаётся, всё не-pip-и-не-bin считается
  `"system-other"`.
- **Ручная проверка** — страница настроек → «зависимости» → кнопка
  «проверить обновление» (`tools/settings.py: /api/check_ytdlp`, всегда
  форсирует свежий запрос, минуя кэш). Результат — «обновлён», «доступна
  новая версия X (у вас Y)» или текст ошибки; кнопка сама переключается в
  «обновить» при найденной новой версии — по клику дёргает
  `POST /api/ytdlp_update_do` → `core.do_ytdlp_update()` (способ — по
  источнику, см. выше), тот же роут, что и у тоста на главной.
- **Автоматическая фоновая** — при каждом открытии главной страницы (`/`)
  фронт дёргает `/api/ytdlp_update_check`; если версия устарела — **не
  блокирующее** уведомление плавающим блоком в нижней части экрана (не
  перекрывает интерфейс). Кнопка «обновить» есть только если источник
  `"bin"`/`"pip"` — для `"system-other"` тост просто просит обновить вручную,
  без кнопки. Крестик в кружке закрывает без обновления, запоминается в
  `sessionStorage` на конкретную версию — повторно за ту же версию в рамках
  вкладки не побеспокоит.

Механика проверки версии не изменилась: сравнивается локальная версия
(`yt-dlp --version`) с последним релизом на GitHub
(`api.github.com/repos/yt-dlp/yt-dlp/releases/latest`, через `urllib.request`
— без сторонних HTTP-библиотек). Результат кэшируется на **30 минут**
(`core._YTDLP_UPDATE_CACHE_TTL`), чтобы не дёргать GitHub API на каждое
открытие главной страницы и не упереться в анонимный rate-limit.

### ffmpeg / Deno — без автообновления

Стабильные зависимости, version-diff и фоновый опрос GitHub им не нужны. В
настройках → «зависимости» — только статус (найдено/нет, расположение: «в
папке приложения (bin/)» / «в системе») и кнопка «переустановить», которая
заново открывает то же окно установки (см. выше), не выполняя скачивание
напрямую — пользователь снова выбирает из трёх вариантов, даже если
компонент уже на месте (это осознанная переустановка, а не «не найдено» —
заголовок окна меняется на «переустановка компонентов»).

## Предупреждение о месте на диске

При каждом открытии главной страницы фронт дёргает `/api/disk_check`
(`core.check_disk_and_cache()`). Если срабатывает хоть одно из двух условий —
**красный баннер** в верхней части главного экрана (над плитками, не
перекрывает интерфейс) с понятным текстом и ссылкой «открыть настройки →»:

- свободного места на диске (там, где лежит `DOWNLOADS_DIR`) меньше
  `DISK_FREE_WARN_BYTES` — по умолчанию **2 ГБ**;
- суммарный размер кэша + временных файлов jade.tools больше
  `CACHE_TEMP_WARN_BYTES` — по умолчанию **5 ГБ**.

Оба порога — константы в начале секции «Место на диске» в `core.py`, их
можно поменять прямо в коде (в UI настроек порогов нет — по ТЗ это
осознанное решение автора функции, не пользовательская настройка). Результат
кэшируется на 60 секунд (`core._DISK_CHECK_TTL`) — обход папки кэша
рекурсивный и не бесплатный, а страница может перезагружаться часто.

## Дизайн

Моноширинный шрифт **IBM Plex Mono**, акцент — jade-зелёный. Вся палитра —
CSS-переменные в `templates/_base.html` (`--bg`, `--surface`, `--surface-2`,
`--text`, `--muted`, `--accent` и т.д., плюс семантические `--error*`/
`--success*` для сообщений об ошибке/успехе); новые страницы наследуют её
автоматически. Тексты в интерфейсе — строчными буквами (нижний регистр),
лаконичный «терминальный» стиль.

### Тема

Тёмная (по умолчанию) и светлая — переключаются на странице настроек,
применяются сразу на всех открытых страницах, без перезагрузки.

- **Механизм** — атрибут `data-theme="dark"|"light"` на `<html>`, светлая
  палитра переопределяет те же переменные под селектором
  `[data-theme="light"] { ... }` в `templates/_base.html`. Акцент в светлой
  теме затемнён (`#178f66` вместо `#21c98a`) — исходный зелёный слишком
  светлый для контраста на белом фоне.
- **Первый рендер без вспышки** — значение `theme` из настроек кладётся в
  `data-theme` уже на сервере: `app.py` инжектит его во все шаблоны через
  `@app.context_processor` (`core.get_settings()["theme"]`), поэтому
  `<html>` рождается сразу с правильной темой, без доли секунды не в той
  теме до JS.
- **Мгновенное переключение** — на странице настроек смена селекта
  (`data-key="theme"`) идёт по двум путям параллельно: обычное автосохранение
  (`POST /settings/api/save`, тот же механизм, что у всех полей) и отдельный
  листенер, который сразу ставит `data-theme` на `<html>` — не дожидаясь
  ответа сервера и без перезагрузки. Другие уже открытые вкладки/страницы
  подхватят новое значение при следующей навигации (серверный рендер).
- **Валидация** — допустимы только `"dark"`/`"light"`. Всё остальное (в том
  числе устаревшее `"custom"` от более старой версии, если уже лежит в
  чьём-то `settings.json`) тихо приводится к `"dark"` и на чтении
  (`core.load_settings()`), и на сохранении (`core.save_settings()` и
  `tools/settings.py: api_save`) — без ошибки, без падения приложения.
- **Цвета вне переменных** — там, где фон принципиально не должен зависеть
  от темы (плашки-таймкоды поверх волны/видеоряда в «нарезать» — `.corner`,
  `.zoomhint`; модальный оверлей; тени), цвет остаётся фиксированным
  намеренно, с комментарием в коде почему.
- **Canvas в «нарезать»** — волна и плейхед рисуются на `<canvas>`, поэтому
  CSS-переменные им не подходят напрямую: цвета читаются в JS через
  `getComputedStyle(document.documentElement).getPropertyValue("--...")`
  (`ACCENT`/`TEXT_COLOR`/`LINE_COLOR` в `templates/trim.html`) при загрузке
  скрипта — тот же паттерн для всех трёх цветов волны/плейхеда/заглушки.

**Иконки — [Lucide](https://lucide.dev/icons/)**, inline-SVG без внешних
зависимостей (важно: приложение локальное/офлайн). Набор иконок и автозамена
по `data-icon="name"` живут в `templates/_base.html` (`window.ICONS` +
`document.querySelectorAll("[data-icon]")`). Чтобы добавить иконку: взять SVG
с lucide.dev → вписать `<path>`-содержимое в объект `P` внутри `ICONS` →
использовать как `<span data-icon="name"></span>` в разметке или
`ICONS.name` в JS (для динамически генерируемых подписей/кнопок).

## Cookies и доступ к YouTube

YouTube активно усложняет скачивание. Для полноценной работы инструментов с
YouTube-ссылками обычно нужны **две вещи**: cookies (против «Sign in to
confirm you're not a bot») и **JavaScript-рантайм** (для решения JS-проверки
подписи, без которого отдаются только превью-картинки). Это ограничения со
стороны YouTube, а не баг приложения.

Всё это касается не только YouTube — все три инструмента принимают ссылку с
**любого сайта, который поддерживает yt-dlp** (TikTok, Instagram, Vimeo и
т.д.; полноценные плейлисты — только с YouTube). Но именно YouTube почти
всегда требует cookies, поэтому ниже речь в основном о нём.

> **Cookies — по умолчанию ВЫКЛЮЧЕНЫ** (`use_cookies=False`) и подключаются
> только если пользователь явно включил их в настройках (раздел «Пути» →
> «использовать cookies»). Выключены → `core.cookies_args()` всегда отдаёт
> пустой список, cookies не подключаются ни при каких обстоятельствах —
> двух попыток (см. ниже) тоже нет, ровно один вызов yt-dlp.
>
> **Включены — подключаются «по мере необходимости», а не вслепую всегда.**
> На любой ссылке `run_ytdlp_json_ex()` / `detect_playlist()` /
> `run_ytdlp_download()` делают ровно две попытки в противоположные стороны
> (без cookies / с cookies); порядок решает `core._first_attempt_cookies()`:
> если вложенный тумблер «подтягивать автоматически из браузера» включён (по
> умолчанию при включении cookies) — первая попытка сразу **с cookies** (не
> тратить вызов вслепую, когда YouTube их и так почти всегда потребует); если
> выключен (настроен файл) — первая попытка **без cookies**. Если и вторая
> попытка не помогла — пользователю показывается её ошибка (обычно
> информативнее).
>
> Почему не «всегда добавлять cookies для всех сайтов» (и почему вторая
> попытка нужна независимо от того, что шло первым): устаревшие или просто
> «чужие» для конкретного сайта cookies из того же `cookies.txt`/браузера
> сами способны триггерить его антибот. На практике так и вышло — TikTok
> стабильно отвечал HTTP 403 именно из-за лежащих в общем `cookies.txt` кук
> для `tiktok.com` (сохранённых туда заодно с YouTube-куками), хотя без
> cookies то же видео скачивалось мгновенно. Двусторонний fallback защищает
> от обеих ситуаций сразу, независимо от того, в каком порядке настроены
> попытки: если сайту cookies нужны — они рано или поздно подключатся; если
> не нужны и вредят (как оказалось у TikTok) — попытка без них рано или
> поздно решит вопрос.
>
> EJS-солвер (следующий раздел) — историю не повторяет: он подключается
> автоматически только для youtube.com/youtu.be ссылок, поскольку решает
> исключительно JS-проверку подписи YouTube и другим сайтам не нужен, и не
> зависит от настройки cookies.

### 1. JavaScript-рантайм (Deno)

Если в логе/ошибке встречается **«Signature solving failed»**, **«n challenge
solving failed»** или **«Only images are available»** — `yt-dlp` не смог решить
JS-проверку и не получил форматы. Нужен JS-рантайм Deno — `core.py` сам найдёт
его в типичных местах установки winget и подмешает в `PATH` процесса
(`ensure_js_runtime_on_path`), даже если он не виден в `PATH` запущенного
exe/трея. Подробности — <https://github.com/yt-dlp/yt-dlp/wiki/EJS>.

> Ошибка **HTTP 429 (Too Many Requests)** — временный лимит запросов с вашего
> IP. Просто подождите 10–30 минут.

### 2. Cookies

Управляется на странице **настроек** (раздел «Пути»), прогрессивное
раскрытие в три состояния (`templates/settings.html`):

```
[ ] использовать cookies                        ← главный тумблер, выкл по умолчанию
     выключен → блока ниже нет вовсе (cookies не подключаются никогда)
     включён  → появляется вложенный тумблер:

     [✓] подтягивать автоматически из браузера   ← вложенный тумблер
          включён (по умолчанию при раскрытии) → дропдаун браузера
          снят → поле пути к cookies.txt + инструкция экспорта
```

Снятие вложенного тумблера — это «переключиться на файл», а НЕ «выключить
cookies»: за выключение отвечает только главный. Хранится как
`use_cookies` (главный) / `cookies_from_browser` (вложенный, значим только
при `use_cookies=True`) / `cookies_browser` / `cookies_file_path`
(`core.DEFAULT_SETTINGS`); настройки, сохранённые до этого разделения
(`cookies_file` без главного тумблера), мигрируют автоматически при первой
загрузке (`core.load_settings()`) — `use_cookies` выводится из того, был ли
раньше настроен файл или включена автоподтяжка, чтобы не потерять молча уже
работавшую конфигурацию.

- **«Подтягивать автоматически из браузера»** (по умолчанию при раскрытии) —
  дропдаун **только Firefox и его форки** (LibreWolf, Waterfox, Zen) —
  намеренно, не «Firefox по умолчанию, остальные тоже можно»:
  Chromium-браузеры (Chrome, Edge, Opera, Opera GX, Brave, Yandex) с 2024
  применяют app-bound encryption — ключ расшифровки cookies привязан к
  самому браузеру, внешний процесс (yt-dlp) прочитать их не может в принципе,
  не только «может не сработать». Firefox и форки хранят cookies в открытом
  SQLite — работают без ограничений, куки читаются заново при каждом
  скачивании, не устаревают.
  У yt-dlp нет отдельных ключевых слов `--cookies-from-browser` для LibreWolf/
  Waterfox/Zen (проверено: `yt_dlp.cookies.SUPPORTED_BROWSERS` = Chromium-браузеры
  `| {firefox, safari}`) — для них `core._resolve_cookies_browser_spec()`
  резолвит путь к профилю вручную (`%APPDATA%\LibreWolf`, `%APPDATA%\Waterfox`,
  `%APPDATA%\zen`) и передаёт как `firefox:<путь>`: хранилище cookies у форков то же
  Mozilla-совместимое SQLite, а `yt_dlp._extract_firefox_cookies` принимает
  произвольный путь как корень поиска (`cookies.sqlite` в нём самом, прямых
  подпапках и `Profiles/*/` — то, что соответствует реальной раскладке).
  Выбранный браузер не установлен или ни разу не запускался → понятная
  ошибка «Не удалось найти профиль браузера…» (`core.friendly_ytdlp_error()`
  по подстроке `could not find ... cookies database`), а не сырой стек
  `CookieLoadError` от yt-dlp.
- **Свой `cookies.txt`** (работает с **любым** браузером — экспорт делает сам
  пользователь расширением внутри браузера, инструкция не привязана к
  Firefox) — раскрывающаяся инструкция прямо на странице настроек:
  установите «Get cookies.txt LOCALLY» (Chrome/Edge/Opera/Brave — Chrome Web
  Store; Firefox — Firefox Add-ons), откройте youtube.com и войдите в
  аккаунт, экспортируйте (формат Netscape) и укажите путь на странице
  настроек. Раз в время **переэкспортируйте заново** — сессионные токены в
  файле устаревают; страница настроек показывает дату последнего изменения
  файла как подсказку.

> **OAuth2 в yt-dlp намеренно НЕ реализован** — плагин архивирован
> (январь 2026), официальная OAuth2-поддержка yt-dlp нестабильна, не решает
> PoToken-проверки YouTube, плохо ложится на архитектуру web-UI приложения и
> несёт риск для аккаунта пользователя. cookies — единственный поддерживаемый
> способ авторизации.

> Cookies дают доступ к вашему аккаунту — не передавайте `cookies.txt` третьим
> лицам.

## Запуск в трее — готовый .exe

`tray_app.py` поднимает Flask в фоновом потоке и показывает иконку в системном
трее. Сборка — **onedir** (не onefile): PyInstaller кладёт `jade.tools.exe` и
папку `_internal/` (DLL, Python, упакованные `templates/`+`logo.ico`) в общую
папку `dist\jade.tools\`, без установленного Python — удобно класть в
автозапуск. Перенести приложение можно только вместе с `_internal/` — без неё
exe не запустится.

> **Почему не onefile.** Раньше сборка была onefile (один самораспаковывающийся
> exe). У бета-тестера Windows Defender удалил такой exe как
> `Trojan:Win32/Sabsik.TE.A!ml` — эвристическое ложное срабатывание, типичное
> для onefile-сборок PyInstaller именно из-за самораспаковки во `%TEMP%` при
> каждом запуске. Onedir не распаковывается никуда — exe запускается напрямую
> из своей папки, поведенческий триггер пропадает.

### Сборка

```bat
build.bat
```

> ⚠️ **Перед каждой пересборкой закройте запущенный экземпляр** (`jade.tools.exe`
> в трее, или `py app.py`/`py tray_app.py` из исходников) — иначе exe залочен и
> соберётся старый/битый бинарь. `build.bat` сам этого не делает.

Скрипт проверит зависимости, сгенерирует `logo.ico` (если нет) и соберёт по
`jade.spec`. Результат — `dist\jade.tools\jade.tools.exe` + `dist\jade.tools\_internal\`.
Следом `build.bat` копирует `readme.txt` в `dist\jade.tools\` — шагом ПОСЛЕ
PyInstaller, а не через `datas` в `jade.spec`: файл, упакованный в бандл, лёг
бы в `_internal/`, а не рядом с exe (та же особенность `sys.executable` vs
`__file__`, см. CLAUDE.md — при onedir `sys._MEIPASS` тоже указывает внутрь
`_internal/`, но пользовательские пути (`BASE_DIR`) по-прежнему считаются от
`sys.executable`, так что `bin/`/`temp/`/`cache/`/`logs/` создаются рядом с
exe, а не внутри `_internal/`). В конце скрипт ждёт нажатия клавиши (`pause`),
поэтому окно не закрывается само — в том числе и при ошибке, её текст
останется на экране.

### Проверки при старте (только в собранном exe)

Две проверки в `tray_app.py`, обе пропускаются при запуске из исходников
(`py app.py`/`py tray_app.py`, `sys.frozen` не выставлен):

- **Запуск из временной папки** (`core._is_temp_launch()` /
  `core.RUNNING_FROM_TEMP`) — если `BASE_DIR` оказался внутри `%TEMP%`/`%TMP%`
  (типичный случай — распаковка exe архиватором прямо из архива без
  извлечения), приложение всё равно стартует (Flask, браузер), но на КАЖДОЙ
  странице (`app.py: _inject_temp_launch`, context processor) показывается
  блокирующая модалка (`templates/_base.html`, `#tempLaunchModal`) — без
  крестика и клика по фону: единственная кнопка «закрыть приложение» дёргает
  `POST /api/quit` (чистит задачи и завершает процесс `os._exit(0)`, тот же
  эффект, что «Выход» из трея) и пытается закрыть вкладку браузера
  (`window.close()` срабатывает не всегда — вкладку открыл Python, не
  скрипт, — тогда на её месте остаётся текст «можно закрыть вручную»).
- **Целостность ресурсов** (`tray_app._check_resources_or_die()`) — до
  запуска Flask и открытия браузера проверяет, что все реально используемые
  `templates/*.html` и `logo.ico` есть внутри `sys._MEIPASS`. Веб-модалка
  здесь невозможна — она сама живёт в `_base.html`, то есть ровно в файлах,
  чьё отсутствие проверяется, поэтому при нехватке файлов — нативный
  `tkinter.messagebox.showerror` со списком недостающего и выход
  (`os._exit(1)`). Не проверяет внутренности самого PyInstaller-бандла (DLL,
  tcl/tk) — их отсутствие роняет бутлоадер раньше, чем выполнится код Python.

> Сообщения самого `build.bat` — на английском, и в нём намеренно нет
> `chcp 65001`: сочетание переключения кодовой страницы с кириллицей в
> том же bat-файле — известный баг `cmd.exe`, ломающий построчный разбор
> скрипта (многобайтовые UTF-8-символы режутся на куски, и обрывки текста
> пытаются выполниться как отдельные команды). Само приложение как было на
> русском, так и осталось — это только про консольный вывод сборочного
> скрипта. Если всё же что-то пойдёт не так, соберите вручную — это всё,
> что `build.bat` делает на последнем шаге:

```bat
py -m PyInstaller --noconfirm --clean jade.spec
```

### Чистый экспорт проекта (`make_clean_zip.bat`)

```bat
make_clean_zip.bat
```

Собирает `.zip` со снимком проекта **по принципу whitelist** — копируются
только явно перечисленные в скрипте файлы/папки, всё остальное исключается
по умолчанию (в том числе новые файлы, которые появятся в проекте позже и
о которых забудут упомянуть в списке). При запуске — интерактивное меню:

- **1) для ревью кода** — `app.py`, `core.py`, `tray_app.py`, `make_icon.py`,
  `jade.spec`, `requirements.txt`, `build.bat`, `logo.png`, `logo.ico`,
  `tools\*.py`, `templates\*.html`.
- **2) для GitHub** — то же самое, плюс `README.md`, `ARCHITECTURE.md`,
  `LICENSE`, `.gitignore`, `readme.txt`, папка `assets\` целиком (скриншоты,
  гифы, обе GitHub-иконки). `make_clean_zip.bat` в свой же экспорт для
  GitHub НЕ включён — dev-скрипту нечего делать в публичном репозитории. Если
  какого-то из этих файлов нет на диске, предупреждение в консоли, файл
  просто пропускается, выполнение не прерывается.

Никогда не попадают в архив (даже если появятся в проекте в будущем):
`.claude\`, `CLAUDE.md`, `MEMORY.md`, `dist\`, `build\`, `__pycache__\`,
`downloads\`, `settings.json`, `cookies*.txt`.

Имя архива — `jade.tools_{VERSION_NUMBER}_review.zip` или `..._github.zip`
(версия читается из `tools/settings.py`; если прочитать не удалось — вместо
номера версии подставляется текущая дата `YYYYMMDD_HHMM` с предупреждением
в консоли). В режиме «для GitHub» скрипт дополнительно сверяет дату
`dist\jade.tools.exe` с самым свежим файлом кода — если код новее, выводит
предупреждение пересобрать exe перед публикацией релиза (сам exe в архив
не попадает в любом случае). Копирование идёт во временную папку
`_clean_export\`, архивируется через `Compress-Archive` (PowerShell) и
удаляется. В конце — полный список файлов, реально попавших в архив, чтобы
свериться, не открывая сам zip.

> Как и `build.bat`, этот скрипт написан на английском и без `chcp 65001` —
> по той же причине (см. предупреждение выше).

> **На будущее.** `make_clean_zip.bat` собирает исходники для ревью/GitHub,
> не релизный архив с exe. Если позже появится отдельный скрипт сборки
> релизного `.zip` (готовый exe для пользователей), его whitelist обязан
> включать папку `_internal\` **целиком** — без неё собранный архив будет
> нерабочим (onedir, см. «Запуск в трее» выше).

### Трей-версия

- Запуск exe → иконка в трее, через ~1.5 с сам открывается браузер.
- Меню (правый клик): **Открыть в браузере**, **Папка загрузок**
  (`downloads/` рядом с exe), **Выход**. Двойной клик = «Открыть в браузере».
- Повторный запуск exe закрывает прошлый экземпляр (один экземпляр в трее).
- Флаг `--autostart` — тихий старт без авто-открытия вкладки (для ярлыка в
  автозагрузке Windows). Альтернативный способ добиться того же при любом
  запуске — галочка «запускать без открытия вкладки браузера» в настройках
  (`core.DEFAULT_SETTINGS["no_browser_on_start"]`); действуют по логике «ИЛИ»,
  ни один не перезаписывает другой (см. `tray_app.main()`).
- В собранном виде рабочие файлы лежат в `downloads/` **рядом с exe** (ресурсы
  Flask распаковываются во временный `_MEIPASS`, а пользовательские данные — нет).

### Автозапуск Windows

`Win+R` → `shell:startup` → создать ярлык на `jade.tools.exe`. Чтобы вкладка
не открывалась именно при автозапуске (а при обычном запуске открывалась как
всегда) — допишите `--autostart` в конце поля «Объект» ярлыка, а не включайте
галочку в настройках (она подавляет вкладку при ЛЮБОМ запуске).

## Возможные проблемы

- **«Не удалось получить информацию» / «подтвердить, что вы не бот» / «требует
  решения JS-проверки»** — нужны cookies и/или JS-рантайм Deno (см. раздел
  «Cookies и доступ к YouTube»). Также обновите `py -m pip install -U yt-dlp`.
- **«Не удалось найти профиль браузера»** — в настройках выбран Firefox/
  LibreWolf/Waterfox/Zen, который не установлен в системе или ни разу не
  запускался (см. «Cookies и доступ к YouTube» → «2. Cookies»). Дропдаун
  сознательно ограничен Gecko-браузерами — Chromium (Chrome/Edge/Opera/Brave/
  Yandex) с 2024 не отдаёт cookies внешним процессам (app-bound encryption,
  [yt-dlp#10927](https://github.com/yt-dlp/yt-dlp/issues/10927)) в принципе,
  поэтому такой режим для них даже не предлагается — используйте файл
  `cookies.txt`.
- **«module mutagen was not found»** (постпроцессинг) — yt-dlp нужен
  Python-модуль mutagen для встраивания обложки/метаданных в аудио:
  `py -m pip install mutagen` (в тот же Python, где установлен yt-dlp).
  Либо выключите «встраивать обложку и метаданные» в настройках.
- **«Не удалось прочитать cookies: браузер запущен…»** — режим «куки из
  браузера» работает только при закрытом браузере (запущенный лочит базу
  cookies). Закройте его или перейдите на `cookies.txt`.
- **HTTP 429** — временный лимит запросов YouTube; подождите 10–30 минут.
- **Видео+звук не сливается / сжатие падает** — `ffmpeg` должен быть в `PATH`.
- **Целевой размер слишком мал** (в сжатии/нарезке+сжатии) — увеличьте размер
  в МБ либо уменьшите битрейт звука: на коротком фрагменте даже минимальный
  битрейт может не влезть.
- **Залочен exe при сборке** — закройте работающий экземпляр (см. выше).
- **Не открывается диалог «обзор…» в настройках** — нужен `tkinter` (включён в
  сборку, см. `jade.spec`); при запуске из исходников должен идти в комплекте
  со стандартным Python на Windows.

## Переопределения окружения (для разработки)

В дополнение к странице настроек (правит `settings.json`, применяется во время
работы без перезапуска), на уровне процесса можно переопределить:

- `YTD_HOST` / `YTD_PORT` (или `PORT`) — адрес и порт сервера (переменные окружения).
- `MAX_FILE_BYTES` (в `core.py`) — лимит размера отдаваемого файла (0 = без лимита).
- Путь к `yt-dlp`/`ffmpeg`/`ffprobe`/`deno` переменной окружения не
  переопределяется — резолвится автоматически (`bin/` → `PATH`, см.
  «Резолвинг внешних зависимостей»); чтобы явно закрепить конкретный
  бинарник, положите его в `bin/` рядом с приложением.
